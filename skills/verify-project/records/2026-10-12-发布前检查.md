## 二、双向验证（防橡皮章）—— 方案 B：注入缺陷

**做法**：临时把 `.gitignore` 第 10 行的 `.env` 改成 `#.env`（= 故意让机密文件失去保护），
跑检查、看它红不红，然后 `git checkout -- .gitignore` 还原。

### 2.1 ⚠️ 第一次注入：**漏报，逮到了**

| 步骤 | 结果 |
|---|---|
| 注入 `.gitignore` L10：`.env` → `#.env` | 第 10 行确认已变成 `#.env` |
| 跑 `check-offline.mjs` | **A2 竟然还是 ✅**，退出码 **0** —— **漏报** |

**根因**：第一版 A2 判据写的是「有 `.env` 行，**或**有 `.env.*` 行」。
看着合理，其实**错**：Git 里 `.env.*` 只匹配 `.env.production` 这类带后缀的，
**挡不住 `.env` 本身**。于是 `.env` 被注释掉之后，`.env.*` 还在，检查器照样放行。
⇒ **一个会放行"本该拦的"检查器，等于没有。**

### 2.2 修正

把 A2 从「找关键词」改成**按 Git 的真实语义逐行判**：
从前往后扫，最后一条命中的规则说了算，`!` 开头是例外（把文件捞回来）。
用 glob→正则做匹配（`*` → 非 `/` 任意串），只处理根级模式（本项目规则都在根级）。

改完后同一个 `.gitignore` 的判定结果：

| 目标 | 真实仓库 | 注入后（`.env` 被注释） |
|---|---|---|
| `.env` | 被忽略（命中 `.env`） | ❌ 没有任何规则挡住它 |
| `.env.example` | 未被忽略（可进仓库，正确） | 未被忽略 |

### 2.3 第二次注入验证：**能抓了**

注入保持不动，跑修正后的检查：

```
  ❌ A2  .env 被 .gitignore 挡住（且 .env.example 仍能进仓库）
       ↳ 按 Git 语义判定：.env ❌ 没有任何规则挡住它 —— 会被提交上去！ ｜ .env.example 未被忽略（可进仓库，正确）
退出码：1
```

⇒ **同一次注入，修前绿、修后红** —— 这就是 checker 不是橡皮章的证据。

### 2.4 还原

```
git checkout -- .gitignore
```

| 核对项 | 结果 |
|---|---|
| 第 10 行 | 已回到 `.env` |
| `git diff --stat -- .gitignore` | **空**（Git 认为与 HEAD 一致） |
| `git hash-object .gitignore` | `14ce6cc4184a7e498d12bbe32240c257e72c8835` |
| `git rev-parse HEAD:.gitignore` | `14ce6cc4184a7e498d12bbe32240c257e72c8835` ← **一致** |
| ⚠️ sha256 变了 | `aefd1b3d…` → `7bcebaf9…`。原因：本机 `core.autocrlf=true`，`git checkout` 把工作区的 LF 还原成 CRLF（72 个 CR / 72 个 LF）。**行尾变了，内容没变**，Git 侧完全一致。 |
