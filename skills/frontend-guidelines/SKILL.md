# 前端准则自查

## 用途

把「什么样的筛选交互才算做对」写成**能自动跑的检查**，而不是靠人自觉。

它只认一件事：项目里的**筛选 / 列表交互**，有没有同时守住两组底线 ——

1. **三态齐全**：有结果 / 无结果 / 清空后能恢复；
2. **可访问**：键盘能走到、读屏能念对、切换时不把用户的位置弄丢。

**这段是硬契约**：检查跑出红条还当没看见，等于这次自查没做。

## 何时使用

用户提到以下任一意图时使用本 skill：

- 「检查筛选」「筛选交互自查」「跑一遍前端规范」
- 「检查可访问性」「a11y 查一下」「键盘能走吗」
- 「我这个列表页的三种状态对不对」

**不适用**：性能/包体积分析、CSS 视觉审查、后端接口检查。
本 skill 只做「筛选交互的**结构与语义**检查」，不评判好不好看。

## 检查项（10 条，逐条对账）

| 编号 | 检查什么 | 怎么算过 |
|---|---|---|
| F1 | **有结果**：按当前筛选条件过滤出列表 | 存在过滤函数（`.filter` 按条件取子集），且列表渲染确实用它 |
| F2 | **无结果**：筛选命中 0 条时给人话 | 有空列表分支，且分支里给出**可见文案**（不是留白） |
| F3 | **清空恢复**：条件清空后回到全量 | 过滤函数里有「条件为空 → 返回全部」的兜底 |
| A1 | 控件语义：筛选键是 `<button>` | 生成筛选键的标签是 `<button`，不是 `<a>` / `<div>` |
| A2 | 选中态语义：互斥开关用 `aria-pressed` | 筛选键上带 `aria-pressed` |
| A3 | 当前项语义：正打开的那条用 `aria-current` | 列表项上带 `aria-current` |
| A4 | 焦点保留：切换时只改属性、不重铺整排 | 切换函数体内**不调用**重铺整排的渲染函数 |
| A5 | 容器可命名：列表容器有 `aria-label` | 容器标签上带 `aria-label` |
| S1 | 数据驱动：选项来自 JSON，不写死在页面 | 选项清单从数据文件读，页面上只留空壳 |
| S2 | 切筛选先停播：别留「看不见的播放器」 | 切换函数体内先调停止播放 |

**为什么 A4 单独拎出来**：重铺整排按钮会把用户刚点的那个键换掉，
键盘焦点跟着丢，读屏软件还得从头再念一遍。这是最容易被忽略、又最伤键盘用户的一条。

## 如何调用（两个工具，缺一不可）

### 工具一 · 静态检查（读源码，零依赖）

```bash
node skills/frontend-guidelines/scripts/check-filter-interaction.mjs [项目根目录]
```

- 参数省略时，默认查当前工作目录。
- 输出：逐条 ✅ / ❌ 一行，末尾给汇总。
- **退出码 0 = 全部通过；1 = 有未通过项；2 = 读不到文件（项目根传错）。**
  ⚠️ 以退出码为准，**不要靠肉眼扫代码**。

### 工具二 · 真机三态验证（真开浏览器点一遍）

```bash
NODE_PATH=<受管 Node 工作区的 node_modules> \
node skills/frontend-guidelines/scripts/verify-three-states.cjs [项目根目录]
```

- 验 ①有结果 ②无结果（L2 / L3）③清空恢复，外加一条可访问性：切换后焦点没被弄丢。
- **默认不开本地服务器**：请求被拦下、直接从磁盘读文件喂回去。
  原因：项目自带的 `dev-server.js` 硬绑 `0.0.0.0`（线上平台需要），
  在公共热点下用它验证等于把整个项目摊给同网段的人。设 `BASE_URL` 才改走真实服务。
- 依赖本机 Edge ＋ `playwright-core`；`BROWSER_PATH` 可换别的浏览器。

### 两个工具的分工

静态检查答「代码里**写了**吗」，真机验证答「点下去**真的对**吗」。
**只跑一个不算做完自查。**

### 双向验证（这不是橡皮章）

两个工具都按「正常代码通过 + 故意改坏报警」两头验过，明细见 `records/`：

| 工具 | 正常代码 | 故意改坏的副本 |
|---|---|---|
| 静态检查 | 10/10 · 退 0 | 7/10 · 退 1 |
| 真机三态 | 5/5 · 退 0 | 1/5 · 退 1 |

坏副本一律建在系统临时目录，**验完即删，不进仓库**。

## 人还要做的那一步（脚本替不了）

两个脚本都跑绿之后，剩下这一步必须人来做：

1. 打开跟读页，**自己按一遍**：L1（有结果）→ L2 / L3（无结果）→ 切回 L1（清空恢复）；
2. 三步各留一张截图，**图里要含地址栏、筛选条件与结果**。

为什么脚本绿了还要人看：脚本验的是「行为对不对」，
看不出「空状态那句话读起来顺不顺」「筛选后的版面有没有塌」。
这一步缺了，自查只算做了一半。

## 输出格式

```
【前端准则自查】目标：<项目根>
F1 ✅ 有结果：...
F2 ✅ 无结果：...
...
----------------------------------------------------------------
汇总：10/10 通过 · 退出码 0
```

有未通过项时，失败那条会附「期望 / 实际」两行，直接指出该文件里没找到什么。

## 已知边界（诚实说明）

- 静态检查器是**源码启发式**（正则 / 字符串），不是编译器：它认的是「这段处理**存在**」。
  「点下去真的对」由真机脚本负责，两者互补，缺一不可。
- 规则与具体实现**松耦合**：函数重命名、逻辑重写都可能让检查失效（误报）。
  改完交互后若某条突然变红，先看是不是改了名字，再决定改代码还是改规则。
- 真机脚本写死了本机环境（Edge 路径 ＋ 受管 Node 工作区的 `playwright-core`）。
  换机器要改 `BROWSER_PATH` / `NODE_PATH`，或用 `BASE_URL` 走真实服务。
- 真机脚本只点「等级筛选 → 文件列表」这条链，不碰播放、不碰首页。
- 只覆盖筛选 / 列表交互这一块，跟本项目其它页面无关。

## 常见故障

| 现象 | 原因 | 处理 |
|---|---|---|
| `找不到文件 assets/js/app.js` | 项目根传错了 | 用项目根目录（含 `index.html` 的那层）重跑 |
| 全条 ❌ 一起红 | 路径不对，读的是空内容 | 同上，先确认能读到文件 |
| 某条红但你确信代码是对的 | 函数/属性被改名，规则没跟上 | 改规则里的锚点，或按新写法补一条 |
| 中文输出乱码 | Windows 终端代码页 | 加 `chcp 65001`，或看写出的报告文件 |
